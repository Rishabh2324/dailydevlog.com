## Course philosophy

1. **Problem before tool.** Every technology is introduced as the answer to a problem you've already hit.
2. **Build it by hand, then use the framework.** Raw `fetch` before an SDK. Cosine similarity by hand before a vector database. A hand-written tool loop before an agent framework.
3. **Evaluate from week 3.** You can't improve a probabilistic system you don't measure.
4. **Security, cost and observability are part of every project**, not a final chapter.
5. **TypeScript first.** Python only where the ecosystem really requires it (fine-tuning, model internals).
6. **No vendor lock-in.** Provider-specific APIs are labeled as such.

Claims are labeled as **Fact**, **Best practice**, **Opinion** or **Emerging** throughout, and fast-moving lessons carry a "last verified" date.

## Traditional vs AI architecture

```
TRADITIONAL                     AI APPLICATION
UI                              UI  (streaming, partial state, approvals, citations)
 ↓                               ↓
API                             API / BFF  (auth, quotas, stream proxy)
 ↓                               ↓
Business logic                  Orchestrator  (deterministic control, prompts, budgets)
 ↓                               ↓         ↘               ↘
Database                        LLM(s)     Retriever → Vector/search DB
                                 ↓          Tools → External APIs / MCP servers
                                Validation + guardrails (deterministic again)
                                 ↓
                                Response + trace + cost record + eval sample
```

| Concern | Traditional | AI |
|---|---|---|
| Correctness | Tests prove it | Evals estimate it statistically |
| Behavior source | Code | Code + prompt + model version + retrieved data |
| Latency | Milliseconds | Seconds, streamed |
| Cost | Mostly fixed infrastructure | Per request, variable, attacker-inflatable |
| Security | Injection solved by parameterization | Prompt injection has no complete fix; contain it architecturally |
| Dependencies | Versioned libraries | Models get deprecated and change behavior |

**16-week variant (~1–1.5h/day):** Same order, with 2–3 weeks each for Seasons 2, 4 and 5, plus dedicated weeks for local models and fine-tuning.

## Don't learn this yet

| Skip for now | Why |
|---|---|
| Backprop derivations, linear algebra and calculus courses | Intuition is enough for application engineering |
| Training models from scratch, PyTorch in depth | A researcher/ML engineer skill with little payoff for building products |
| CUDA, GPU kernels, distributed training | Specialized infrastructure roles |
| LangChain or LlamaIndex before hand-building RAG and agents | Abstractions hide exactly what you need to learn |
| Multi-agent "team" frameworks | Most problems need a workflow, not a team of agents |
| Fine-tuning | Prompting + RAG + evals solve most cases |
| Comparing ten vector databases | pgvector covers most apps until you hit a measured limit |
| GraphRAG, A2A | Niche wins; you don't have the problem yet |
| Chasing model releases and leaderboards | Your own eval set is the benchmark that matters |
| Prompt "hack" lists, no-code agent builders | Short-lived tricks that hide the architecture you're trying to learn |
