## 1. Restate the problem

Given `n` non-negative integers `height` representing an elevation map where the width of each bar is `1`, compute how much water it can trap after raining.

## 2. Inputs, outputs, edge cases

- **Input:** `height` — array of non-negative integers, `1 <= n <= 2 * 10^4`, `0 <= height[i] <= 10^5`.
- **Output:** a single integer — total units of trapped water.
- **Constraints noted:**
  - Water above position `i` is bounded by `min(maxLeft(i), maxRight(i)) - height[i]`, and can never be negative — a strictly increasing or strictly decreasing elevation traps `0` water.
  - The tallest bar overall traps nothing above itself (nothing to its higher side on one edge).
  - Flat terrain (all equal heights) traps `0`.
  - `n == 1` or `n == 2` → no water can be trapped (need a bar on both sides to form a basin).

## 4. Brute force first

For each index, scan left to find `maxLeft` and scan right to find `maxRight`, then add `min(maxLeft, maxRight) - height[i]` if positive.

```ts
function trapBruteForce(height: number[]): number {
  let total = 0;

  for (let i = 0; i < height.length; i++) {
    let maxLeft = 0;
    for (let l = 0; l <= i; l++) maxLeft = Math.max(maxLeft, height[l]);

    let maxRight = 0;
    for (let r = i; r < height.length; r++) maxRight = Math.max(maxRight, height[r]);

    total += Math.min(maxLeft, maxRight) - height[i];
  }

  return total;
}
```

- **Time:** `O(n^2)` — a left scan and a right scan for every index.
- **Space:** `O(1)`.

## 5. Identify the pattern and optimize

The brute force repeats the same left/right scans over and over. Precomputing `maxLeft[i]` and `maxRight[i]` arrays in two linear passes drops this to `O(n)` time but costs `O(n)` extra space. The **two-pointer** trick removes that space cost: maintain `left = 0`, `right = n - 1`, and running maxes `leftMax`, `rightMax`. At each step, compare `height[left]` and `height[right]` — whichever side is *smaller* has a water level that's already fully determined, because its own running max is guaranteed to be the binding (smaller) constraint regardless of what lies further past the other pointer (the other side's max is already `>=` this side's max, and can only grow). So advance the smaller side: update its running max, add `runningMax - height[pointer]` (never negative, since running max only increases), and move that pointer inward. This resolves one index's water contribution per step in `O(1)` work, giving `O(n)` time and `O(1)` space overall.

## 6. Code it

```ts
function trap(height: number[]): number {
  let left = 0;
  let right = height.length - 1;
  let leftMax = 0;
  let rightMax = 0;
  let total = 0;

  while (left < right) {
    if (height[left] < height[right]) {
      leftMax = Math.max(leftMax, height[left]);
      total += leftMax - height[left];
      left++;
    } else {
      rightMax = Math.max(rightMax, height[right]);
      total += rightMax - height[right];
      right--;
    }
  }

  return total;
}
```

## 7. Test it manually

- `height = [0,1,0,2,1,0,1,3,2,1,2,1]` → matches the hand-traced table above → returns `6` ✓ (LeetCode's expected output).
- `height = [4,2,0,3,2,5]` → two pointers converge with `leftMax`/`rightMax` tracking `4` and `5`; contributions at indices `1,2,3,4` sum to `2+4+1+1=... ` walking through: `left=0(4) < right=5(5)` → leftMax=4, water+=0, left=1; `height[1]=2<5` → leftMax=4, water+=2, left=2; `height[2]=0<5` → leftMax=4, water+=4, left=3; `height[3]=3<5` → leftMax=4, water+=1, left=4; `height[4]=2<5` → leftMax=4, water+=2, left=5, loop ends → total `0+2+4+1+2=9` ✓ (matches known expected output for this example).
- `height = [1,2,3,4]` → strictly increasing; the smaller side is always `left`, `leftMax` tracks `height[left]` exactly so every contribution is `0` → returns `0` ✓.
- `height = [1]` → `left == right` immediately, loop never runs → returns `0` ✓.

## 8. Review and log

- **Approach used:** two-pointer sweep from both ends, always resolving the side with the smaller current height first since its water level is already fully constrained.
- **Mistake to watch for:** advancing the *larger* side, or comparing `leftMax`/`rightMax` instead of `height[left]`/`height[right]` to decide which pointer moves — the correctness proof specifically relies on comparing the raw heights at the pointers, not the running maxes.
- **Recurring pattern to log:** "the smaller of two running bounds is the one that's already fully determined, so resolve it first and move on" is the same greedy insight as `container-with-most-water`, and generalizes to any problem where a value is bounded by `min` of two frontiers that only grow monotonically as pointers advance.

## Complexity

- **Brute force — Time:** `O(n^2)`, **Space:** `O(1)`.
- **Precomputed max arrays — Time:** `O(n)`, **Space:** `O(n)`.
- **Two pointer — Time:** `O(n)` — each pointer moves at most `n` times total. **Space:** `O(1)`.
