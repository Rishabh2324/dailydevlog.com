## 1. Restate the problem

Design and implement a (singly) linked list. Support these operations:

- `get(index)` — return the value of the `index`-th node (`0`-indexed), or `-1` if the index is invalid.
- `addAtHead(val)` — insert a node with value `val` before the first element.
- `addAtTail(val)` — append a node with value `val` after the last element.
- `addAtIndex(index, val)` — insert a node with value `val` before the `index`-th node. If `index` equals the length of the list, append at the end. If `index` is greater than the length, do nothing.
- `deleteAtIndex(index)` — delete the `index`-th node, if it exists.

## 2. Inputs, outputs, edge cases

- **Input:** a sequence of operations on a `MyLinkedList` instance, with integer values and indices.
- **Output:** `get` returns an integer (`-1` for out-of-range); other operations return nothing but mutate the list's state.
- **Constraints noted:**
  - `0 <= index, val <= 1000`, up to `2000` calls total.
  - `get`/`deleteAtIndex` with a negative index, or an index `>=` current length → invalid, `get` returns `-1`, `deleteAtIndex` does nothing.
  - `addAtIndex` with `index <= 0` → same as `addAtHead`.
  - `addAtIndex` with `index == length` → same as `addAtTail`.
  - `addAtIndex` with `index > length` → no-op, list unchanged.
  - Operating on an empty list — every operation must handle a `head` of `null` safely.

## 3. Diagram the structure

**Node shape** — each node holds a value and a pointer to the next node (`null` for the last node):

```
Node { val: 5, next: ● } ---> Node { val: 2, next: ● } ---> Node { val: 8, next: null }
```

**Using a dummy head** simplifies every operation by removing the "is this the first node?" special case — `dummy.next` always points at the real head (or `null` if empty), so insertion/deletion logic is identical whether operating at the front or the middle:

```
dummy ---> [5] ---> [2] ---> [8] ---> null
  ^
  dummy.next === head of the real list
```

**`addAtIndex(1, 9)`** on `dummy -> [5] -> [2] -> [8] -> null` — walk a pointer `prev` from `dummy` forward `index` times (here, `1` step, landing on node `[5]`), then splice a new node `[9]` in between `prev` and `prev.next`:

```
before:  dummy -> [5] -> [2] -> [8] -> null
                    ^prev

splice:  dummy -> [5] -> [9] -> [2] -> [8] -> null
                    ^prev  ^new node's `next` was set to prev.next ([2]) first,
                            then prev.next was repointed to the new node
```

**`deleteAtIndex(2)`** on `dummy -> [5] -> [9] -> [2] -> [8] -> null` — walk `prev` forward `2` steps (landing on `[9]`), then skip over `prev.next` (`[2]`) by relinking:

```
before:  dummy -> [5] -> [9] -> [2] -> [8] -> null
                           ^prev        ^target ([2]) removed by:
                                        prev.next = prev.next.next

after:   dummy -> [5] -> [9] -> [8] -> null
```

## 4. Brute force first

A "brute force" here isn't a different algorithm so much as skipping the dummy-head trick and hand-checking the head as a special case everywhere — it works, but every method needs an extra `if (index === 0)` branch duplicating logic that the dummy node would otherwise unify.

```ts
class Node {
  val: number;
  next: Node | null = null;
  constructor(val: number) {
    this.val = val;
  }
}

class MyLinkedListNaive {
  head: Node | null = null;

  addAtHead(val: number): void {
    const node = new Node(val);
    node.next = this.head; // special-cased separately from addAtIndex's splice logic
    this.head = node;
  }
  // ...addAtTail, addAtIndex, deleteAtIndex each need their own "is head involved?" branch
}
```

- **Time:** still `O(n)` per positional operation — no complexity difference from the optimized version.
- **Space:** `O(n)` for `n` nodes — same as the optimized version; the real cost here is code complexity (duplicated head-special-casing), not asymptotic performance.

## 5. Identify the pattern and optimize

This is a **linked list design** problem where the main technique isn't an algorithmic speedup but a structural simplification: a **dummy head node**. By making `dummy.next` always represent "the real head" (even when the list is empty), every insertion and deletion becomes "find the node before the target position, then relink it" — with no separate branch for "am I inserting/deleting at the front?" This collapses four near-duplicate special cases (head vs. middle vs. tail vs. empty) into one uniform traversal-and-splice pattern reused by `addAtIndex` and `deleteAtIndex`.

## 6. Code it

```ts
class ListNode {
  val: number;
  next: ListNode | null = null;
  constructor(val: number) {
    this.val = val;
  }
}

class MyLinkedList {
  private dummy: ListNode = new ListNode(-1);
  private size = 0;

  get(index: number): number {
    if (index < 0 || index >= this.size) return -1;

    let curr = this.dummy.next;
    for (let i = 0; i < index; i++) {
      curr = curr!.next;
    }
    return curr!.val;
  }

  addAtHead(val: number): void {
    this.addAtIndex(0, val);
  }

  addAtTail(val: number): void {
    this.addAtIndex(this.size, val);
  }

  addAtIndex(index: number, val: number): void {
    if (index > this.size) return;
    if (index < 0) index = 0;

    let prev = this.dummy;
    for (let i = 0; i < index; i++) {
      prev = prev.next!;
    }

    const node = new ListNode(val);
    node.next = prev.next;
    prev.next = node;
    this.size++;
  }

  deleteAtIndex(index: number): void {
    if (index < 0 || index >= this.size) return;

    let prev = this.dummy;
    for (let i = 0; i < index; i++) {
      prev = prev.next!;
    }

    prev.next = prev.next!.next;
    this.size--;
  }
}
```

## 7. Test it manually

Following the classic example sequence:

- `addAtHead(1)` → list: `dummy -> [1] -> null`, `size = 1`
- `addAtTail(3)` → `addAtIndex(1, 3)` → `dummy -> [1] -> [3] -> null`, `size = 2`
- `addAtIndex(1, 2)` → `prev` walks 1 step to `[1]`, splices `[2]` after it → `dummy -> [1] -> [2] -> [3] -> null`, `size = 3`
- `get(1)` → walk 1 step from `dummy.next` → lands on `[2]` → returns `2` ✓
- `deleteAtIndex(0)` → `prev` stays at `dummy` (0 steps), removes `dummy.next` (`[1]`) → `dummy -> [2] -> [3] -> null`, `size = 2`
- `get(0)` → returns `2` ✓ (matches expected output sequence `[null,null,null,null,2,null,3]`)
- `get(5)` on the 2-node list → `5 >= size (2)` → returns `-1` ✓ (out-of-range guarded)
- `addAtIndex(10, 99)` on the 2-node list → `10 > size (2)` → no-op, list unchanged ✓

## 8. Review and log

- **Approach used:** dummy-head-based singly linked list, where `addAtHead`/`addAtTail` are expressed as calls into a single `addAtIndex` primitive, and both add/delete share the same "walk `prev` to just before the target" traversal.
- **Mistake to watch for:** forgetting to increment/decrement `size` after `addAtIndex`/`deleteAtIndex` desyncs the bounds checks in `get`/`deleteAtIndex` from the list's real length; also, splicing in the wrong order (`prev.next = node` before `node.next = prev.next`) loses the rest of the list by pointing `node.next` at itself.
- **Recurring pattern to log:** "dummy node removes head-special-casing" is a staple for linked list problems — reappears in "remove nth node from end," "merge two sorted lists," and "reverse linked list II," anywhere insertion/deletion near the head would otherwise need its own branch.

## Complexity

- **Time:** `O(n)` per positional operation (`get`, `addAtIndex`, `deleteAtIndex`) for the traversal to reach the index; `O(1)` for `addAtHead`.
- **Space:** `O(n)` total for `n` stored nodes; each individual operation uses `O(1)` extra space.
